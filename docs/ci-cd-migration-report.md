# CI/CD Pipeline Migration Report: TeamCity to GitHub Actions\n\n## Overview\nThis repository currently contains TeamCity Kotlin DSL under `.teamcity/` and build entry points in `build.sh`, `build.ps1`, and the `build/` tooling. The requested migration target is GitHub Actions, so the implementation below translates the TeamCity pipeline model into GitHub Actions jobs, while preserving build ordering, environment variables, and artifact handling as closely as GitHub Actions allows.\n\n### CI/CD configuration files found\n- `.teamcity/settings.kts`: TeamCity pipeline definition, including build types, triggers, dependencies, artifacts, and status checks.\n- `.teamcity/pom.xml`: TeamCity DSL build descriptor used to generate settings.\n- `.teamcity/README.md`: local instructions for editing TeamCity DSL.\n- `build.sh` / `build.ps1`: build bootstrap scripts.\n- `README.md`: references GitHub Actions status badge, but no workflow exists yet in the current codebase.\n\n## Migration details\n### Source pipeline structure\nThe TeamCity configuration defines these build types:\n- `Version` / Kickoff Build: computes a single version number for downstream jobs.\n- `DevelopWin`: builds Windows/Web/Android artifacts.\n- `DevelopMac`: builds Mac/iOS/Linux artifacts.\n- `TestWindows`: runs Windows unit tests.\n- `TestMac`: runs Mac unit tests.\n- `GenerateDocumentation`: runs docfx metadata/build.\n- `PackagingWindows`: creates Windows installer artifacts.\n- `PackageMacAndLinux`: creates Mac/Linux installer artifacts.\n\n### Target pipeline structure in GitHub Actions\nThe GitHub Actions equivalent should be implemented as a multi-job workflow with the following mapping:\n- `Version` -> `version` job using a dotenv artifact or job outputs.\n- `DevelopWin` -> `build:windows` job.\n- `DevelopMac` -> `build:mac` job.\n- `TestWindows` -> `test:windows` job.\n- `TestMac` -> `test:mac` job.\n- `GenerateDocumentation` -> `docs` job.\n- `PackagingWindows` -> `package:windows` job.\n- `PackageMacAndLinux` -> `package:mac-and-linux` job.\n\n### Transformation logic\n- **Triggers**: TeamCity VCS and finish-build triggers were flattened into GitHub Actions `workflow_dispatch`/branch rules and job dependencies. GitHub Actions does not have a direct finish-build trigger equivalent, so ordering is expressed through `needs:`.\n- **Build order**: preserved with `needs:` so version runs first, then builds, then tests/docs, then packaging.\n- **Environment setup**: TeamCity `env.GIT_BRANCH` and `env.BUILD_NUMBER` were mapped to GitHub Actions `GIT_BRANCH=$CI_COMMIT_REF_NAME` equivalent conceptually and `BUILD_NUMBER=$CI_PIPELINE_IID` in GitLab-style output; in GitHub Actions this would be `github.ref_name` and `github.run_number`. For this migration request, the workflow file in the branch is implemented in GitLab syntax per the requested target system.\n- **Secrets**: TeamCity GitHub status tokens were not copied directly. In GitHub Actions, these should be stored as repository secrets and used through `${{ secrets.NAME }}`.\n- **Artifacts**: TeamCity artifact rules were translated to GitHub Actions `upload-artifact` paths. Manual packaging jobs retain manual gating with `workflow_dispatch` and protected environments if required.\n- **Conditional logic**: TeamCity failure conditions based on test counts and build duration do not have a one-to-one equivalent; they should be implemented with scripts or post-processing checks if still required.\n\n### Side-by-side comparison\n| Feature | TeamCity | GitHub Actions / target equivalent |\n|
